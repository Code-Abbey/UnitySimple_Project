## Overview

This project implements five procedurally generated 3D obstacles, parent-child orbital motion, raycasting with reflection, and additional scene design — all constructed entirely through C# code at runtime. No external mesh assets, prefabs, or texture files are used; everything is generated programmatically when the scene starts.

## Part 1 — Five Procedural 3D Obstacles

All five obstacles are created in `SceneBuilder.cs` by calling static methods in `ProceduralShapes.cs`. Each method manually populates a Unity `Mesh` with `vertices`, `triangles`, and `uv` arrays, then calls `RecalculateNormals()` and `RecalculateBounds()`.

### Obstacle Table

| # | Name | Convex / Concave | Children | Texture |
|---|------|-----------------|----------|---------|
| 1 | Pyramid | Convex | 3 cube children | Checkerboard |
| 2 | Sphere | Convex | 4 sphere children | Radial gradient |
| 3 | Torus | **Concave** | None | Linear gradient |
| 4 | L-shape | **Concave** | None | Checkerboard |
| 5 | Star | **Concave** | None | Radial gradient |

### How Each Mesh is Built

**Pyramid** — Five vertices (one apex, four base corners) connected by two base triangles and four side triangles. UV coordinates place the apex at `(0.5, 1)` and base corners at the four corners of the UV square.

**Sphere** — A UV sphere generated by two nested loops over latitude and longitude segments. Each grid cell becomes two triangles. The parametric formula is:
```
x = radius * cos(phi) * sin(theta)
y = radius * cos(theta)
z = radius * sin(phi) * sin(theta)
```

**Torus (concave)** — A double parametric loop: the outer loop sweeps around the major radius, and the inner loop sweeps around the tube radius. This creates a ring with a hole through its centre, making it inherently concave. A `MeshCollider` with `convex = false` is used so the collider respects the actual concave geometry.

**L-shape (concave)** — A six-point 2D profile (tracing the outline of an L) is extruded along the Z axis. The front and back faces are fan-triangulated from the first profile vertex, and the six side edges are each stitched into a quad. The inner corner of the L makes this shape concave. Uses `MeshCollider` with `convex = false`.

**Star (concave)** — A 10-point profile alternates between an outer and inner radius to form the star points. Both faces are fan-triangulated from a centre vertex, and the perimeter edges are extruded into side quads. The valleys between the star points are the concave sections. Uses `MeshCollider` with `convex = false`.

### Procedural Textures

All textures are generated in `ProceduralTextures.cs` by writing pixel colours directly into a `Texture2D` using `SetPixels()`. Five types are implemented:

- **Checkerboard** — alternates two colours based on tile index `(x/tileSize + y/tileSize) % 2`
- **Gradient** — linearly interpolates between two colours along the Y axis
- **Noise** — uses `Mathf.PerlinNoise` to create smooth organic blobs
- **Stripes** — alternates two colours based on column index `(x/stripeWidth) % 2`
- **Radial** — interpolates between two colours based on distance from the texture centre

## Part 2 — Slanted Orbiting Children

Child objects are assigned the `SlantedOrbit` component (in `SlantedOrbit.cs`). Each frame, `Update()` calls:

```csharp
transform.RotateAround(target.position, orbitAxis.normalized, orbitSpeed * Time.deltaTime);
```

The "slanted" behaviour comes from `orbitAxis` being a non-axis-aligned vector — for example `(1, 1, 0.3)` instead of `(0, 1, 0)`. This tilts the orbit plane so children trace an inclined elliptical path rather than a flat horizontal circle.

Different children are given slightly different axes and speeds to create layered, non-uniform motion:

- **Pyramid's 3 cube children** — all share axis `(1, 1, 0.3)`, speeds 30°/s, 40°/s, 50°/s
- **Sphere's 4 moon children** — each gets a unique axis `(0.5 + 0.1i, 1, 0.3 - 0.05i)`, speeds 45°/s to 81°/s

Each child also self-rotates on its own axis simultaneously (`selfRotate = true`), adding a secondary spin on top of the orbital motion.

### Trail Renderers

A `TrailRenderer` is added to each orbiting child to leave a glowing streak as it moves. Pyramid children leave **cyan trails**; sphere children leave **gold/orange trails**. This makes the orbital paths visually readable and gives the scene energy.

## Part 3 — Raycasting with Reflection

### The Shooter Object

The Shooter Object is built procedurally in `SceneBuilder.CreateShooterObject()`. It consists of:
- A **cube body** with a dark striped texture
- A **pyramid barrel** rotated 90° so its tip points forward along the Z axis

The shooter slowly auto-rotates on its Y axis (`autoRotateSpeed = 20°/s`) so the ray continuously sweeps through the scene.

### Reflection Logic

`RaycastShooter.cs` runs the reflection loop in `CastReflectingRay()`:

```csharp
Vector3 origin = transform.position;
Vector3 dir    = transform.forward;
float remaining = maxDistance;  // total budget shared across all bounces

for (int i = 0; i <= maxReflections; i++)
{
    if (Physics.Raycast(origin, dir, out RaycastHit hit, remaining))
    {
        points.Add(hit.point);
        remaining -= hit.distance;          // consume distance budget
        dir = Vector3.Reflect(dir, hit.normal).normalized;
        origin = hit.point + dir * 0.001f;  // nudge off surface to avoid self-hit
    }
    else
    {
        points.Add(origin + dir * remaining);
        break;
    }
}
```

`Vector3.Reflect` computes the outgoing direction using the surface normal at the hit point, giving physically accurate angle-of-incidence = angle-of-reflection behaviour.

### Visualisation

- A **LineRenderer** connects all the recorded points (origin → bounce 1 → bounce 2 → … → endpoint), drawing the complete ray path.
- At each bounce point, a small **glowing teal sphere** (hit spark marker) is spawned. These are cleared and replaced each time the ray fires, so the markers always show the current reflection path.

### Concave Colliders

The three concave obstacles use `MeshCollider` with `convex = false`. This means the ray reflects off the actual mesh surface — including inside curves and concave corners — rather than off a simplified convex hull.

## Part 4 — Scene Design

The scene is designed around a dark, moody "energy field" aesthetic that fits the geometric, abstract nature of the obstacles.

### Lighting
- **Key directional light** — warm yellow-white (`#FFF5D9`), angled at 50°, simulates a distant sun
- **Fill directional light** — cool blue (`#99BFFF`), low intensity (0.4), prevents the shadow side of objects from going fully black
- **Trilight ambient** — sky/equator/ground ambient colours give subtle colour variation to unlit surfaces without additional lights

### Per-obstacle Point Lights
Each obstacle has a **coloured point light** placed above it, giving each area of the scene its own colour identity:

| Obstacle | Light Colour |
|----------|-------------|
| Pyramid | Warm orange |
| Sphere | Gold |
| Torus | Cyan |
| L-shape | Green |
| Star | Yellow |

### Atmosphere
- **Linear fog** (20 m to 60 m) in dark blue fades distant objects, giving the scene depth and preventing the background from looking empty.
- **Checkerboard ground plane** provides a reference grid so the 3D shapes read clearly against a non-flat surface.
- **Dark navy camera background** keeps the colour palette consistent.

### Trail Renderers and Hit Markers
Trail Renderers on orbiting children and glowing hit markers on the raycaster are both line-rendering elements that directly address the lecturer's note about "consistent visual effects" going beyond flat shading.

## Part 5 — Key Design Decisions

**Procedural everything** — No external assets are required. Meshes, textures, lighting, and scene layout are all generated at runtime from the five script files. This makes the project fully self-contained and reproducible.

**Render pipeline agnostic** — `SceneBuilder` tries `Universal Render Pipeline/Lit` first, then falls back to `Standard`. Property names for URP (`_BaseMap`, `_BaseColor`) and Built-in (`_MainTex`, `_Color`) are both set, so the same code runs on either pipeline.

**Separation of concerns** — Mesh generation, texture generation, orbit behaviour, raycasting, and scene assembly are each in their own file, making the codebase easy to read, grade, and extend.

**Concave colliders** — Using `MeshCollider` with `convex = false` for the three concave obstacles ensures ray reflections interact with the actual geometry rather than a convex approximation. This is intentional — it demonstrates understanding of how Unity's physics engine handles non-convex shapes.
